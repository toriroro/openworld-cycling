# オープンワールド・サイクリング 仕様概要

2026-11-13 初版。大まかな仕様。細部は各段階の着手時に個別の仕様へ分ける。

同日改訂: keirin-3D を参考に、システム構成（8）・モバイルアプリ（9）・公開と運用（10）・流用表（11.2）を追加・変更。

同日改訂2: ウェブ版優先・横画面基本・BGM は後回し、の決定を反映。iOS 移植の規則（9.5）を追加し、段階計画（13）を組み替え。最初に作る範囲は [モック仕様](2026-11-13-mock.md) に分けた。

記号: 【仮定】= 確認なしで置いた前提（変更可能）。【要判断】= 決めてもらいたい点。

## 1. コンセプト

ほぼ無限に続く1つの世界を、全プレイヤーが共有して自転車で走り続ける。

| 醍醐味 | 仕様上の意味 |
|---|---|
| ほぼ無限遠の共有マップ | 世界は1つ。誰が走っても同じ場所に同じ道・同じ店がある。未踏の地域は誰かが近づいた時点で生成され、以後固定される |
| 多人数で走る | 近くの他プレイヤーが同じ道に見える。広すぎて会えない問題への対策を仕様に含める（5.3） |
| 冬のトレーニング | スマートトレーナーの出力で進み、勾配が負荷に反映される |
| 眺めるだけでもよい | 入力なしで走り続ける自動走行、他プレイヤーの追尾観戦、BGM |
| 多様で相応にリアルな景観 | 海岸・平野・丘陵・山岳・林道（グラベル）・都市を、実寸・写真素材ベースで描く |
| 寄り道 | 喫茶店などの立ち寄り地点。休憩・スタンプ・再開地点・交流の場 |

## 2. 遊び方

### 2.1 3つの乗り方

走行の入力元だけが違い、世界・物理・マルチプレイは共通。

| 乗り方 | 推進力 | 操舵 | 主な端末 |
|---|---|---|---|
| トレーナー | トレーナーの実測パワー(W) | 自動（分岐のみ選択） | PC / Android / iOS アプリ |
| 手動 | キー・タッチ（既定出力＋連打ダッシュ） | 自動または手動 | PC / スマホ |
| 眺める | 仮想ライダーの設定出力（例 150W） | 自動（分岐も自動可） | PC / スマホ / TV |

### 2.2 1回の流れ

1. 開始地点を選ぶ: 前回の続き / 訪問済みの喫茶店 / 起点の町 / 走行中のフレンドや人の多い地域。
2. 走る。分岐で進路を選ぶ。地図に走った道が記録される。
3. 喫茶店・展望地などに寄る。停車すると立ち寄り画面になり、スタンプが付く。
4. 任意の場所で終了。位置は保存され、次回そこから再開できる。

ゴール・コース・制限時間はない。落車による強制終了もない【仮定】（downhill-3D と異なる。癒やし用途を優先）。

## 3. ワールド

### 3.1 方式の比較

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 道路先行の一本道 | 進行方向へ道を伸ばし、周囲に地形を後付け（downhill-3D「ながみね峠」の延長） | 実装が最小。景観を作り込みやすい | 2次元の地図にならない。周回・交差・「あの峠の向こう」が成立せず、共有マップの意味が薄い |
| **B. 地形先行＋道路網（採用案）** | シードから地形・気候を決め、集落と道路網をその上に引く | 本物の地図になる。探索・分岐・周回・共有が成立 | 道路生成（経路探索・切土盛土・橋・トンネル）が技術的な山場 |
| C. 実在地図 | OSM＋標高データで現実の地球を再現（downhill-3D「手稲山」の拡大） | 無限のコンテンツ、土地勘 | データ量・配信・ライセンス表示・建物や植生の欠落。景観品質が地域のデータ次第 |

B を採用【仮定】。「生成し続ける」という要望と、品質を自分で制御できる点から。C の資産（OSM/DEM 取り込み）は将来「実在の峠を世界の一角に置く」用途に残せる。

### 3.2 スケールと座標

- 実寸。単位は m・s・kg。距離・時間・勾配を圧縮しない（トレーナーの負荷と一致させるため、downhill-3D の「高低差2倍表示」は使わない）。
- 世界座標は倍精度の平面座標。地球の曲率は扱わない。描画はカメラ付近を原点に置き直す（浮動原点）。
- 世界の広さは整数のセル番号で決まり、1km セル×32bit で事実上無限。生成は起点から外側へ、誰かが近づいた地域だけ行う。
- 風景の基調は日本風の架空世界、左側通行【仮定】（既存の道路・交通・ガードレール資産と整合）。

### 3.3 生成の階層

| 階層 | セル寸法(目安) | 決めるもの | 生成場所 |
|---|---|---|---|
| 大域 | 30〜60km | 大陸・海・山脈・気候 → 景観タイプ | 端末（シードから計算） |
| 地域 | 8km | 集落・峠・岬などの結節点、道路網、立ち寄り地点 | **サーバーで1回だけ生成して保存** |
| 道路形状 | 道路1本ごと | 中心線・縦断勾配・幅・路面・橋/トンネル（2m 間隔の点列） | 同上（地域データに含む） |
| 近景 | 250m | 地形メッシュ、路肩、植生、建物、小物 | 端末（Web Worker） |

要点:

- **地形の高さ**はシードの関数で、端末ごとに計算する。端末間の微小な計算差は見た目にしか影響しない。
- **道路網と立ち寄り地点**（位相に関わるもの）はサーバーが地域単位で一度だけ生成し、保存して配る。理由は 3.8。
- 道路の近く（道路端から数十m）は道路の高さに地形を合わせる。走行物理は道路データの勾配だけを使う。

### 3.4 景観タイプ

標高・海からの距離・湿潤度・都市度の組み合わせで決める。境界は連続的に混ぜる。

| タイプ | 地形 | 道 | 主な要素 |
|---|---|---|---|
| 海岸 | 海沿いの低地・断崖 | 海岸線に沿う平坦〜小さな起伏 | 砂浜、防波堤、漁港、灯台、岬 |
| 平野・田園 | 平坦 | 直線的、格子状の農道 | 田畑、用水、防風林、集落 |
| 丘陵・里山 | 緩い起伏 | うねる2車線 | 雑木林、茶畑・果樹、ため池 |
| 山岳 | 急峻 | つづら折り、峠、橋、トンネル | 針葉樹林、岩壁、展望地、峠の標識 |
| 林道（グラベル） | 山腹・沢沿い | 狭い未舗装、急勾配 | 密な樹林、沢、ゲート |
| 都市・郊外 | 平野・港 | 街路網、信号は簡略 | 建物群、商店街、河川敷の自転車道 |

初期は 山岳・海岸・平野 の3つから始め、順に増やす。

### 3.5 道路

- 結節点（町・集落・峠・岬）を地域セルに確率配置し、近傍同士を結ぶ。重要度で道路の等級を決める: 幹線（2車線・最大勾配8%）/ 一般道（2車線・10%）/ 山道（1.5車線・12%）/ 林道（未舗装・15%）。数値は初期値。
- 経路は地形の粗い格子上で、勾配・水域・既存道路を費用にした経路探索で決める。急斜面では自然につづら折りになる。費用が閾値を超える区間は橋・トンネルにする。
- 中心線を曲線補間し、縦断勾配を平滑化して 2m 間隔の点列（位置・方位・勾配・曲率）にする。downhill-3D の `RoadPoint` と同じ形。
- 交差点は平面交差の T字・十字のみ。立体交差・信号制御・ラウンドアバウトは対象外。
- 路面は舗装/未舗装で転がり抵抗と見た目・音を変える。
- 行き止まり（岬・林道終点）は意図して作る。U ターンできる。
- 車線数の幅を広げる（2026-11-13 ユーザーの要望、モックの後）: 都市の幹線・国道は片側2車線以上の太い道、山奥は1車線（すれ違い用の待避所つき）。モックでは山道（4.5m）と林道（3.5m）を中央線なしの1車線相当として描いている。

### 3.6 立ち寄り地点

| 種類 | 置かれる場所 | できること |
|---|---|---|
| 喫茶店 | 町、峠の手前、海沿い、見晴らしの良い道沿い | 停車 → 店内/テラス視点、スタンプ、再開地点に登録、居合わせた人が見える、店ごとの BGM |
| 展望地 | 峠・岬・稜線 | 停車して見渡す視点、スタンプ |
| 峠の標識 | 峠の頂点 | 区間（登り）の終点。標高と名称 |
| 町の拠点 | 各町の中心 | 開始地点。人が集まる場所 |

- 店名・地名は地域データに含めて固定する。命名は音節表からの合成（日本風の架空地名）。
- 喫茶店の密度は初期値で「道なりに10〜20km に1軒」程度。山奥の1軒は見つけた価値が出るよう疎にする。
- 立ち寄りは強制しない。通過も可。
- 将来: 最初の発見者の記録、常連表示、店ごとのメニュー。

### 3.7 時間・天候

- 時刻は世界共通の時計。1日＝実時間の数時間に短縮【仮定】（決まった時間帯にしか遊べない人も朝夕を見られる）。
- 天候は地域と時刻から決まり、同じ場所にいる人は同じ空を見る。初期は 晴れ/曇り/霧、後に雨・雪・季節。
- 眺める乗り方では、時刻・天候を自分の画面だけ固定できる（表示のみ。世界は変えない）。

### 3.8 世界の固定と版管理

道路網をサーバーで一度だけ生成して保存する理由:

1. **端末間の一致**。JavaScript の `Math.sin` などは実装依存で、端末ごとに末尾の桁が違い得る。経路探索の分岐がそこで変わると、人によって道が違う世界になる。位相を1か所で決めれば起きない。
2. **生成器を改良できる**。保存済みの地域は凍結され、新しい生成器は未踏の地域にだけ効く。位置・スタンプ・区間記録が壊れない。
3. **「広がり続ける世界」が事実になる**。誰が最初にその地域を開いたかを記録できる。
4. 後から手で直す・イベント用の場所を置くことができる。

制約: 地形の高さ関数（シード→高さ）は公開後に変えられない。変えると保存済みの道路と地面がずれる。P0 で十分に固めてから公開する。地域データには生成器の版番号を持たせる。

オフライン・開発時は同じ生成コードを端末内で実行する（保存先を差し替えられる構造にする）。

## 4. 走行

### 4.1 物理

downhill-3D の縦方向モデルを引き継ぐ: 重力・空気抵抗・転がり抵抗・駆動力・制動、120Hz 固定更新、描画と独立。

- 登りを含む全勾配で使う（既存は下り専用コースだが式は勾配の符号を問わない）。
- 推進力は「入力元から来る出力(W)」を受ける形にする。
- 体重・機材重量・CdA は設定値。トレーナー利用時は体重入力が速度に直結する。
- 下りの速度超過はカーブ手前で自動減速する【仮定】（コースアウトを作らないため）。手動操舵を選んだ場合のみ自分で曲がる。
- 他プレイヤー・交通・動物との接触判定はしない【仮定】。すり抜ける。

### 4.2 トレーナー連携

- 接続: Bluetooth LE。手段は端末ごとに違う（下の「端末ごとの接続手段」）。
  - FTMS (Fitness Machine Service): 出力・ケイデンスの取得、勾配に応じた負荷指示（シミュレーションモード）。
  - Cycling Power Service: パワーメーター単体。
  - Heart Rate Service: 心拍計。
- 負荷: 道路の勾配・転がり抵抗をトレーナーへ送る。「勾配の効き」を 0〜100% で調整（例 50% で 10% の坂が 5% 相当の負荷。速度計算は実勾配のまま）。
- 表示: 出力・ケイデンス・心拍・速度・勾配・距離・獲得標高。既存の「自転車に付いたサイクルコンピュータ」に表示する形を継承。
- 記録: 走行ログを FIT/TCX で書き出す。外部サービスへの自動アップロードは後の段階。
- 対象外（初期）: ERG モードのワークアウト、ANT+、ステアリング機器。
- 端末ごとの接続手段: PC の Chrome/Edge と Android Chrome は Web Bluetooth。iOS は Safari もアプリ内 WebView も Web Bluetooth が使えない認識（着手時に再確認）なので、iOS アプリ（9章）にネイティブの Bluetooth プラグインを入れる。機器との通信は1つのインターフェースにまとめ、Web 用とネイティブ用の実装を差し替える。

### 4.3 操舵と分岐

- 既定は道路追従の自動操舵。車線内の左右位置だけ任意で動かせる。
- 分岐の手前で進路候補を表示し、左/直進/右を選ぶ。未選択なら直進に近い道。行き先を地図で指定すると、分岐は自動で選ばれる。
- 手動操舵（downhill-3D の舵角保持方式）は選択式で残す。

### 4.4 眺める乗り方

- 仮想ライダーが設定出力で走り続ける。進路は「道なり」「未走行の道を優先」「指定した目的地へ」から選ぶ。
- 視点: 一人称・後方・俯瞰・ドローン・TV（既存5種）に、一定間隔で切り替わる自動演出を加える。
- 他プレイヤーを追尾して眺めることもできる（相手が許可している場合）。
- 眺めているだけのライダーも世界に表示される。実際に漕いでいる人と区別できる印を付ける【仮定】。
- 長時間表示を前提に、画面焼け対策（HUD の非表示）と省電力（フレームレート上限）を設ける。

## 5. マルチプレイ

### 5.1 同期

- 同期するのは位置のみ。道路上の座標（道路ID・道のり・左右位置・速度・向き）を、速度や進路が変わった時と数秒ごとに送る。受信側は道路形状に沿って先読み・補間する。接触判定がないので、これで足りる。
- 世界を区画に分け、区画ごとに1つの接続先（Durable Object）を置く。自分の区画と視界に入る隣の区画の情報だけ受け取る。区画は初期は数十km 角と大きく取り、人が増えた地域から細かくする（費用は「人がいる区画の数」で決まるため。10章）。
- サーバーは走行を計算しない。keirin-3D はレースの計算をサーバーで回して全員に配るが、本作は各端末が自分の走行を計算し、サーバーは中継だけする。
- サーバーは速度の妥当性だけ検査する。トレーナーの出力の真偽は検証できない。
- 通信が切れても一人で走り続けられる。再接続で復帰する。

### 5.2 表示とやり取り

- 近距離は骨格付きモデル、遠距離は簡略表示。名前の札は切替式。
- やり取りは定型の合図（手を振る、ベル、スタンプ）のみ【仮定】。自由入力のチャットは置かない（監視の負担を避ける）。
- 名前は入力制。不適切語のフィルター、報告の手段、「他プレイヤーの名前を表示しない」「自分の名前を出さない」設定を持つ（keirin-3D が App Store 審査向けに実装済みの方式）。
- 一緒に走る: フレンドの位置から開始、同じ目的地の共有。ドラフティング（空気抵抗の軽減）は後の段階。

### 5.3 広すぎて会えない問題

世界が無限だと人が散って誰にも会えない。対策を最初から入れる。

- 開始地点を集約する: 起点の町、人の多い地域を開始候補の上位に出す。
- 地図に「いま人がいる場所」「よく走られている道」を表示する。
- 走行の痕跡を残す: 少し前にそこを走った人の影（非同期の再生）を表示する。
- 喫茶店・町の拠点を人が溜まる場所にする（停車中の人が見える）。
- 人がいない場所は、車・歩行者・動物・NPC ライダー（既存資産）で寂しさを抑える。

## 6. 進行と記録

- 個人: 総距離・獲得標高・走行時間、走った道の地図（未走行は地形だけ見える）、スタンプ帳、到達した峠。
- 世界: 地域の最初の到達者、道ごとの通行回数。
- 区間記録: 峠の登りを自動で区間にし、タイムを残す。順位表は入力元（トレーナー/手動）で分ける。初期は個人記録のみ【仮定】。
- 経験値・レベル・通貨・装備の販売は置かない【仮定】。
- アカウント: ゲストで全機能を使える。任意のアカウント（ユーザーIDとパスワードのみ）で端末間の引き継ぎができ、アプリ内から削除できる【仮定】（keirin-3D と同じ方式）。

## 7. 映像と音

- 目標は「実写ではないが、写真素材と実寸に基づく自然な風景」。downhill-3D の現行水準（写真由来の路面・地表、CC0 の樹木・岩、骨格付きライダー）を出発点にする。
- 広大さの表現に遠景が要る: 近景（〜数百m、高精細）・中景（〜数km）・遠景（山並み・海・町の輪郭、〜数十km）の3段階で地形を描き、大気の霞で繋ぐ。
- 画質は 標準/軽量 の2段階（既存方式）。目標は PC 60fps、中位スマホ 30fps。常駐メモリは走行距離によらず一定。
- 文言は操作・状態・事実情報に限る。雰囲気を説明する文章は置かない【仮定】（downhill-3D の `AGENTS.md` の方針を継承）。
- 音: 環境音（風・路面・交通、既存の合成音を拡張。波・鳥・虫・雨を追加）と BGM。
- BGM: 後の段階で決める（決定 2026-11-13）。手続き生成で落ち着いた曲が作れればそれでもよい。優先する要件は「端末で流している好きな音楽を止めずに、ゲームの環境音を重ねられること」。PC のブラウザでは元から止まらない。iOS・Android で止めずに済むかは実機で確かめる（9.5 の音の規則）。

## 8. システム構成

downhill-3D と keirin-3D に共通する土台（TypeScript / Vite / Three.js / Cloudflare）を使う【仮定】。全体の形は keirin-3D に合わせる: 1つのソースからウェブ版と iOS アプリを作り、1つの Worker が静的ファイルと `/api/*` を受け持つ。

```
src/ ──(build)──▶ dist/ ──▶ Cloudflare Workers（ウェブ版 ＋ /api）
                      └──(Capacitor)──▶ iOS アプリ ──(GitHub Actions の macOS)──▶ TestFlight ──▶ App Store
```

| 部分 | 役割 | 手段 |
|---|---|---|
| 画面 | 描画・入力・音・HUD | Three.js。UI は 3D の上に重ねる DOM（フレームワークなし。keirin-3D の作法） |
| 近景生成 | 地形メッシュ・植生・建物の配置 | Web Worker、結果は型付き配列で受け渡し |
| 世界生成（共有コード） | 高さ関数・景観判定・道路網生成 | 端末とサーバーで同じ TypeScript |
| API | アカウント、セーブ同期、記録、地域データの配信、公開中の版の確認 | Worker（`/api/*` だけ処理。他は静的ファイル） |
| 地域データ | 道路網・立ち寄り地点の一度きりの生成と保存 | Worker で生成、D1 に保存（大きくなれば R2）、CDN キャッシュ |
| 位置共有 | 区画ごとの接続と配信 | Durable Objects（WebSocket、ハイバネーション） |
| 状況とお知らせ | 接続人数、人のいる地域、アプリ内お知らせ | 全体で1つの Durable Object（keirin-3D の OnlineHub と同じ役割） |
| 記録 | 利用者・スタンプ・区間・到達記録 | D1（番号順のマイグレーション） |
| 機器 | トレーナー・心拍計 | Web Bluetooth / ネイティブ BLE プラグイン |
| 端末差の吸収 | 保存先、振動、画面の常時点灯、接続先、機器の実装の切替 | `platform` 層（keirin-3D の `src/platform.ts`・`src/storage.ts` と同じ役割） |

サーバーの仕事は「地域データの一度きりの生成」「位置の中継」「記録」だけで、地形の描画データは配らない。

環境は本番と確認用の2つ。確認用は別の Worker と D1 で、iOS の確認用ビルドはそこへつなぐ（keirin-3D の `env.staging` と同じ）。

## 9. モバイルアプリ

### 9.1 対応端末

| 端末 | 配布 | トレーナー接続 |
|---|---|---|
| PC | ブラウザ | Web Bluetooth |
| Android | ブラウザ（ホーム画面に追加）。ストア公開は後の段階 | Web Bluetooth |
| iPhone / iPad | App Store のアプリ（Capacitor で同じ dist を包む）。ブラウザでも手動・眺めるは使える | アプリのみ（ネイティブ BLE プラグイン） |

開発は Windows のまま行い、iOS のビルド・署名・TestFlight への送信は GitHub Actions の macOS 環境で行う（keirin-3D で運用中の方法。Mac は不要）。

### 9.2 keirin-3D と変える点

| 項目 | keirin-3D | 本作 |
|---|---|---|
| 画面の向き | 縦固定 | 縦・横の両対応。横画面を基本に設計し、縦は配置替えで成立させる（決定 2026-11-13） |
| 対応端末 | iPhone のみ | iPhone と iPad【仮定】（トレーナーの前に置く画面として iPad を想定） |
| 画面の消灯 | 扱っていない | 走行中・眺めている間は消灯させない（プラグインが要る） |
| ほかのアプリの音 | 実機確認の項目 | 自分の音楽を流しながら使えることを要件にする（他アプリの再生を止めない） |
| Bluetooth | なし | 利用目的の申告と接続の許可が要る |
| 裏に回った時 | レースを一時停止。オンラインは CPU が代走 | 走行を一時停止し、世界からは一時退出。戻ると同じ位置に再表示 |
| 同梱データ | 重いモデルをアプリから外している | 世界は生成するので同梱は素材のみ。地域データは取得して端末に保存 |
| 連続動作時間 | 1レース数分 | 数十分〜数時間。発熱・電池・メモリを重点的に確認 |

### 9.3 引き継ぐ作法

- 最低対応 iOS とビルドの変換先をそろえる（keirin-3D は iOS 16.0 と `safari16`。ずれると古い端末で真っ白になる）。
- 画面端は CSS の safe-area で避ける。ダブルタップ・ピンチの拡大を無効にする。
- セーブを WebView の保存領域とネイティブ領域の両方に置く（iOS が WebView のデータを消すことがあるため）。
- 実機確認の項目表（タッチ、画面端、音、裏に回す、セーブ、発熱・電池・メモリ）を流用し、Bluetooth・常時点灯・縦横の切替を足す。
- 既知の制約: iOS では WebAudio の音が画面収録で崩れる（keirin-3D で調査して見送り）。audio 要素を多く使う作りは iPhone で動作が重くなった。BGM の実装方式を決める時に考慮する。

### 9.4 審査に関わる項目

- 他プレイヤーの名前が見えるので、ユーザー生成コンテンツの扱いになる。フィルター・報告・非表示設定が要る（5.2）。
- アカウントは任意で、アプリ内から削除できること。ゲストで全機能が使えること。
- プライバシーの申告: ユーザーID とゲームのデータ。心拍や走行記録をサーバーに保存すると健康・フィットネスの区分に当たり得るので、初期は心拍をサーバーへ送らない【仮定】。
- 生成する地名・店名に実在の名称や商標が出ないよう、除外表で照合する。

### 9.5 iOS 移植で困らないための規則

ウェブ版を先に仕上げる（決定 2026-11-13）。その間も次を守る。後から直すと全体に波及するものだけを挙げる。

| # | 規則 | 理由 |
|---|---|---|
| 1 | 描画は WebGL2。WebGPU 専用の機能に依存しない | iOS 16 の WebView で動かすため |
| 2 | ビルドの変換先に `safari16` を含める | 古い iPhone で真っ白になるのを防ぐ（keirin-3D の実例） |
| 3 | SharedArrayBuffer・Atomics を使わない。Worker とは転送できる ArrayBuffer でやり取りする | アプリ内 WebView では使えない前提で作る |
| 4 | OffscreenCanvas での描画、Service Worker、Fullscreen API、Pointer Lock を必須にしない | iOS で使えない・挙動が違うものがある。あれば使う、なくても成立させる |
| 5 | 端末の機能は `platform` 層の関数を通す: 保存、画面の常時点灯、振動、Bluetooth 機器、外部リンク。`localStorage`・`indexedDB`・`navigator.bluetooth`・`navigator.wakeLock` を各所から直接呼ばない | アプリではネイティブの実装に差し替える |
| 6 | API は1か所から呼び、接続先を差し替えられるようにする。認証は Cookie ではなくトークン | アプリは別オリジンから本番サーバーへつなぐ |
| 7 | 音はすべて1つの音モジュール（WebAudio）を通す。audio/video 要素で鳴らさない。最初の操作で再生を開始する | 他アプリの音楽との共存を1か所で設定するため。iPhone では audio 要素の多用が重かった（keirin-3D の調査） |
| 8 | UI はマウスの hover とキーボードを前提にしない。入力はポインターイベントで統一。押す対象は 44px 以上。画面端は safe-area で避ける。縦でも横でも崩れない | タッチ端末とノッチ |
| 9 | 描画量とメモリの上限を画質設定として持ち、軽量設定を常に動く状態に保つ | iPhone の WebView はメモリ上限が厳しい |
| 10 | 素材・フォントは同梱し、外部の CDN から読まない | オフライン起動と審査 |
| 11 | 浮動小数点テクスチャへの描画など、端末差の大きい GPU 機能を必須にしない | iOS の GPU で使えない場合がある |

上の表の「使えない」は執筆時点の認識で、実機では未確認。iOS アプリの段階（P4）の最初に確かめる。

## 10. 公開と運用

keirin-3D の運用規則を引き継ぐ。

- ウェブ版はデプロイで全員がすぐ新しくなる。アプリ版は審査中と未更新の人の分だけ古い版が残る。そのため API は後方互換を保つ（項目を消さない、意味を変えない）。
- 位置共有の通信の形を変えたら通信の版番号を上げる。版が違うアプリは位置共有だけ断られ、一人では走り続けられる。
- サーバー側の設定値で新しい挙動を入れたり止めたりできるようにする。
- ウェブ版は公開中の版を定期的に確かめ、新しい版があれば読み込み直しを勧める。
- 世界のデータに固有の規則:
  - 地域データの形式に版を持たせる。古いアプリは知らない地物を汎用の見た目で表示する。
  - 新しい景観タイプを未踏地域に出し始めるのは、対応したアプリの公開と同時にする。
  - 高さ関数は変えない（3.8）。
- デプロイすると Durable Objects は作り直され、接続が切れる。keirin-3D はレースが途切れるので専用の手順を持つが、本作は位置が一時的な情報なので自動の再接続で足りる【仮定】。
- 費用: Durable Objects は起きている時間で課金される。keirin-3D の記録では1つを開け続けると月に約 $4。本作は「人がいる区画の数 × 時間」で決まり、眺める利用者が長時間つなぐことが前提になる。対策:
  - 区画を大きく取り、起きている数を抑える。
  - 送信頻度を抑える。一人しかいない区画ではさらに間隔を延ばして眠らせる。
  - 同時の区画数・接続数に上限を置く。連投する接続を切る。
  - 非常時に位置共有だけを止める手段を用意する（一人での走行は続けられる）。
  - 公開前に最悪時の見積もりを作る（keirin-3D の docs/online.md「乱用と課金の対策」と同じ形）。
- 運用の道具: 利用状況の集計、アプリ内お知らせ、アンケート、端末内のエラー記録。

## 14. 主なリスク

| リスク | 影響 | 対応 |
|---|---|---|
| 道路生成の品質（不自然な線形、地形との段差、交差点の破綻） | 体験の中心が崩れる | P0 を道路に集中させる。勾配・曲率・貫通を自動検査する |
| 高さ関数を公開後に変えられない | 景観の改良が未踏地域の道路にしか効かない | P0・P1 を端末内生成で回し、公開（P3）までに固める |
| 遠景を含む描画負荷、スマホ実機が未検証 | 眺める用途で発熱・電池消費 | 画質2段階、フレームレート上限。P1 で実機計測 |
| 人が散って会えない | 「共有」の価値が出ない | 5.3 の対策。必要なら世界の公開範囲を当面絞る |
| iOS のネイティブ BLE プラグインが要件を満たさない（FTMS への書き込み、接続の安定、Capacitor の版との対応） | iOS でトレーナーが使えない | P4 の最初に実機で確認する。満たさなければ小さな自作プラグインにする |
| 位置共有の費用が接続時間に比例して増える | 眺める利用者が長時間つなぐと費用が膨らむ | 10章の対策。P3 の前に見積もる |
| 縦横両対応と iPad 対応で UI の作業が増える | P1 が延びる | HUD を最小限に保つ。先に横画面を固め、縦は配置替えで対応 |
| BGM・素材の権利 | 公開できない | 出典記録の徹底（既存の作法）。15章の判断 |
| 景観の単調さ（生成物は飽きやすい） | 探索の動機が弱まる | 景観タイプの境界、稀な地物（灯台・長い橋・山奥の店）、地域固有の名前 |

## 15. 仮定と未決事項

本文に置いた仮定（異なる場合は指示で差し替える）:

1. 架空の世界を手続き生成する（3.1 の B）。日本風・左側通行。
2. 道路網はサーバーで一度生成して固定、地形は端末で計算する。
3. 落車・接触・コースアウトなし。
4. ウェブ版と iOS アプリを同じソースから出す（keirin-3D と同じ形）。Android は当面ブラウザ。
5. やり取りは定型の合図のみ。成長要素・通貨なし。
6. 時刻は世界共通で、実時間より速く回す。
7. 新規プロジェクトとして作り、downhill-3D と keirin-3D からは必要部分を移す。両プロジェクト側は変更しない。
8. iOS アプリは iPhone と iPad の両対応。
9. アカウントは任意（ユーザーIDとパスワード）。ゲストで全機能を使える。
10. ウェブと App Store で一般公開する前提で、名前の審査・報告・費用の上限を設計に含める。
11. iOS のトレーナー接続は P4 でネイティブ BLE プラグインにより対応する。

決定済み（2026-11-13）:

- 画面は縦・横の両対応。横画面を基本に設計する。
- ウェブ版を先に仕上げる。iOS アプリはその後。ただし 9.5 の規則を最初から守る。
- BGM は後で決める。手続き生成も可。端末で流している音楽との共存を優先する。

決めてもらいたい点:

- **ゲームの名前とドメイン。** ウェブ版を一般公開する P3 の前に決める。それまでは仮称で進める。
- **バンドルID。** App Store Connect への登録後に変更できない。P4 の前に決める。
- **BGM の作り方。** 候補は (a) 権利の明確な既存曲、(b) 自作・委託、(c) コードで合成（keirin-3D に土台がある）。モックでは作らない。
